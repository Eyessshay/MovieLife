# MovieLife 项目功能实现学习指南

## 1. 这份文档解决什么问题

这不是接口清单，也不是简单罗列用了哪些技术，而是从学习和面试角度回答三个问题：

1. 这个功能为什么需要这样设计；
2. 一次请求进入系统后，代码按什么顺序执行；
3. MySQL、Redis 和 Java 代码分别负责什么。

本文以当前 Stage 16 冻结代码为准。接口的完整请求参数、响应字段和错误码仍以 `API接口设计.md` 为准；本文重点解释实现思路。

## 2. 先建立整体认识

MovieLife 是一个 Java 后端项目，主线不是单纯的电影 CRUD，而是：

```text
用户登录
  -> 发现电影 / 活动 / 附近场馆
  -> 查看场次和座位图
  -> Redis 临时锁座
  -> MySQL 创建订单并占座
  -> 支付、出票
  -> 场馆员工核销
  -> 取消、超时或退款时恢复库存

内容侧：
用户评价 / 动态 / 点赞 / 收藏 / 关注
  -> Feed 分发
  -> 评价变化触发 AI 摘要异步生成
```

### 2.1 技术栈

| 层次 | 技术 | 在本项目中的用途 |
| --- | --- | --- |
| Web 层 | Spring Boot 2.7、Spring MVC | 接收 HTTP 请求、参数校验、统一响应 |
| 持久层 | MyBatis-Plus、MySQL 8 | 保存最终业务事实，执行事务、行锁和条件更新 |
| 缓存与并发 | Spring Data Redis、Redis 7、Lua | 登录态、缓存、GEO、点赞、Feed、Stream、临时锁座 |
| 通用组件 | Validation、Jackson、Hutool、Lombok | DTO 校验、JSON 转换、ID/验证码生成、减少样板代码 |
| 工程交付 | Maven Wrapper、Docker Compose、PowerShell | 构建、基础设施启动、演示数据和自动业务验收 |

### 2.2 一次普通请求怎样流转

```text
HTTP 请求
  -> RefreshTokenInterceptor：尝试从 Redis 恢复当前用户
  -> LoginInterceptor：接口带 @LoginRequired 时检查登录
  -> Controller：接参数，不写复杂业务
  -> Service：校验业务规则、组织流程、控制事务
  -> Mapper：查询或条件更新 MySQL
  -> Redis：按功能承担缓存、临时状态或消息通知
  -> VO + Result：返回统一 JSON
```

代码目录的职责：

- `controller`：定义 URL 和 HTTP 方法；
- `dto`：接收请求参数；
- `service` / `service.impl`：业务规则和事务编排；
- `mapper`：数据库读写；
- `entity`：数据库表对应对象；
- `vo`：返回给前端的对象；
- `interceptor`：登录态恢复和登录校验；
- `job`：订单超时、AI 消息消费等后台任务；
- `resources/lua`：必须由 Redis 原子执行的多步操作。

## 3. MySQL 和 Redis 的总职责

这是理解项目最重要的边界。

### 3.1 MySQL 保存最终事实

MySQL 中的数据即使应用重启、Redis 清空，也必须能说明业务最终处于什么状态，例如：

- 用户、电影、活动、场馆、影厅、物理座位；
- 场次和场次座位状态；
- 订单、订单明细、票码、核销信息；
- 评价正文与评分聚合；
- 关注、收藏、动态；
- AI 摘要任务和已发布摘要。

### 3.2 Redis 保存临时状态、关系索引或加速数据

Redis 在本项目中承担：

- 五分钟验证码和一分钟发送限流；
- 一小时登录 Token；
- 电影、场馆、AI 摘要缓存；
- 场馆 GEO 坐标索引；
- 评价和动态的点赞用户集合；
- 关注 Feed 时间线；
- 五分钟临时座位锁；
- AI 摘要 Stream 通知。

关键原则：Redis 的“临时锁座成功”不等于座位已经卖出。只有创建订单的 MySQL 事务成功，座位才从 `AVAILABLE` 变成 `HELD_BY_UNPAID_ORDER`；支付后才变成 `SOLD`。

## 4. 用户登录与接口鉴权

### 4.1 要解决的问题

项目没有实现密码登录和真实短信，而是实现了“手机号 + 验证码”的完整后端流程。重点是防止验证码频繁发送、重复使用，并让登录态可以自动续期。

### 4.2 实现步骤

#### 发送验证码

1. Controller 接收手机号并由 DTO 完成格式校验；
2. Service 对 `login:code:limit:{phone}` 执行 `SET NX`，设置 60 秒 TTL；
3. Key 已存在说明一分钟内重复发送，直接拒绝；
4. 生成 6 位验证码，写入 `login:code:{phone}`，TTL 为 5 分钟；
5. 如果验证码写入失败，删除限流 Key，避免用户无故被限流。

#### 验证码登录

1. Lua 脚本在 Redis 内一次完成“读取验证码、比较、删除”；
2. 验证成功后验证码立即失效，防止同一验证码被并发使用两次；
3. 按手机号查询 MySQL 用户，不存在则自动注册；
4. 生成随机 Token；
5. 写入 `login:token:{token} -> userId`，TTL 为 60 分钟；
6. 把 Token 和用户基本信息返回客户端。

#### 访问受保护接口

1. `RefreshTokenInterceptor` 从 `Authorization: Bearer ...` 解析 Token；
2. 从 Redis 查询 userId，放入基于 `ThreadLocal` 的 `UserHolder`；
3. 刷新 Token 的 60 分钟 TTL，形成滑动过期；
4. `LoginInterceptor` 只拦截标注了 `@LoginRequired` 的方法；
5. 请求结束后清理 `ThreadLocal`，避免线程复用造成用户串号。

### 4.3 关键代码

- `UserServiceImpl`：验证码、登录、退出；
- `RefreshTokenInterceptor`：恢复登录态和续期；
- `LoginInterceptor`：判断接口是否必须登录；
- `WebMvcConfig`：保证“先恢复用户，再检查登录”的拦截顺序。

## 5. 电影发现与详情缓存

### 5.1 功能

- 按关键词、状态、分类、地区分页查询电影；
- 查询电影详情；
- 登录用户在列表和详情中直接看到 `collected` 状态。

### 5.2 实现思路与步骤

电影列表的组合条件很多，当前直接查询 MySQL，避免为任意组合制造大量缓存 Key。电影详情更适合缓存，采用 Cache Aside：

1. 先读取 `movie:detail:{id}`；
2. 命中正常 JSON，反序列化后返回；
3. 命中空字符串，说明这是“空值缓存”，直接返回电影不存在；
4. 未命中时查 MySQL；
5. MySQL 不存在则缓存空字符串 2 分钟，防止同一不存在 ID 反复穿透数据库；
6. MySQL 存在则缓存 30～40 分钟的随机 TTL，避免大量 Key 同时过期；
7. Redis 故障时降级查 MySQL，不让缓存故障拖垮核心查询；
8. `collected` 是当前用户状态，不能放入公共详情缓存，因此在读取公共缓存后单独查询并组装。

演员在数据库中暂存为逗号分隔字符串，Service 返回详情时转换为 `List<String>`。

## 6. 场馆、影厅与 Redis GEO 附近查询

### 6.1 功能

- 场馆列表、详情、影厅列表；
- 查询某场馆某天的电影场次；
- 按坐标、距离、城市和场馆类型查询附近场馆；
- 可进一步筛选“附近且有指定电影/活动未来场次”的场馆。

### 6.2 为什么用 Redis GEO

普通 MySQL 条件查询适合城市、类型、名称筛选，但不擅长高频的圆形范围距离计算。Redis GEO 能按经纬度和半径快速返回候选场馆及距离。

### 6.3 实现步骤

1. 场馆坐标写入 `venue:geo:{city}:{venueType}`；member 是 venueId；
2. 查询时调用 Redis GEO radius，要求返回距离并按近到远排序；
3. Redis 只负责给候选 ID，MySQL 再检查场馆是否启用、城市和类型是否一致；
4. 如果请求还带电影或活动筛选，再批量查询未来有效场次；
5. 过滤没有相应场次的场馆；
6. 保留 GEO 距离顺序并分页组装 VO。

这里没有盲信 Redis：GEO 是加速索引，场馆是否有效仍以 MySQL 为准。

场馆详情缓存与电影详情相同，也有空值缓存、随机 TTL 和 Redis 故障降级。

## 7. 活动发现与固定座位活动

### 7.1 功能

- 活动列表、详情、未来场次；
- 附近活动；
- 活动收藏、评价和 AI 摘要；
- 固定座位活动复用电影票务链路。

### 7.2 附近活动怎样实现

附近活动不是把活动本身直接放进 GEO，因为活动没有唯一地点，同一活动可以在多个场馆有多个场次。实现流程是：

1. 用 Redis GEO 查出附近场馆；
2. 用 MySQL 校验场馆事实；
3. 批量查询这些场馆的未来 Activity 场次；
4. 批量加载 Activity 和 Hall，避免逐条查询形成 N+1；
5. 同一活动可能匹配多个场馆或场次，只选择最合适的一条展示；
6. 按距离、开场时间、活动 ID 形成稳定顺序；
7. 最后补充当前用户的收藏状态。

### 7.3 为什么电影和活动共用场次表

`tb_showtime` 使用 `biz_type + biz_id` 指向 `MOVIE` 或 `ACTIVITY`。锁座、订单、支付和出票只依赖场次与座位，不需要写两套票务代码。Service 层负责校验多态关联，因为数据库无法用一个普通外键同时指向两张业务表。

## 8. 收藏

### 8.1 功能

用户可以收藏电影、活动、动态和评价，并查看自己的收藏列表。

### 8.2 实现步骤

1. 把 targetType 规范化为 `MOVIE/ACTIVITY/POST/REVIEW`；
2. 校验目标真实存在且可见；
3. 查询是否已有收藏，有则直接成功，实现 PUT 幂等；
4. 插入 `tb_collection`；
5. 数据库唯一键 `(user_id, target_type, target_id)` 兜住并发重复请求；
6. 取消收藏直接按三元组删除，重复删除也成功；
7. 收藏列表先分页查关系，再批量加载目标对象，避免 N+1。

收藏是需要长期保留的业务事实，因此存在 MySQL，而不是只放 Redis。

## 9. 关注、动态、点赞与 Feed

### 9.1 关注

关注关系存放在 `tb_follow`。Service 禁止关注自己，先校验目标用户，并用唯一键保证并发幂等。共同关注的实现是查询两人的关注 ID 集合后取交集。

### 9.2 发布动态

1. 登录用户提交标题、正文、图片和可选的关联电影；
2. 校验关联电影存在；
3. 在 MySQL 事务中插入 `tb_post`；
4. 查询作者的粉丝；
5. 只有数据库提交成功后，才把 postId 推入每个粉丝的 `feed:{userId}` ZSet；
6. ZSet score 使用发布时间戳，天然支持按时间倒序读取。

这属于“推模式 Feed”：发布时多写，读取时很快，适合项目当前规模。

### 9.3 Feed 滚动分页

普通页码在不断有新内容插入时容易重复或遗漏。项目使用 `maxTime + offset`：

1. 按 score 从大到小读取一页；
2. 返回本页最小时间戳作为下一页 `maxTime`；
3. 如果多条动态时间戳相同，用 offset 记录已经读过多少条；
4. 批量从 MySQL 加载动态，并保持 Redis 中的顺序；
5. Redis 中引用已删除动态时，顺便清理脏 member。

### 9.4 动态点赞

点赞关系放在 `post:like:{postId}` ZSet，member 是 userId，score 是点赞时间；MySQL 的 `liked` 保存展示计数。

1. `ZADD NX` 成功才给 MySQL 计数加一；
2. 重复点赞不会重复加数；
3. 取消点赞用 Lua 原子执行“读取旧 score + 删除”；
4. 确实删掉关系才把 MySQL 计数减一；
5. 数据库更新失败时把 Redis 关系补回或删回，尽量恢复一致。

## 10. 评价、评分聚合与评价点赞

### 10.1 功能

- 用户对电影或活动创建、修改、软删除评价；
- 一个用户对同一目标只能有一条评价；
- 评分只允许 1.0～5.0，步长 0.5；
- 电影或活动保存 `avg_score` 和 `score_count`；
- 评价可点赞，详情返回当前用户是否点过赞。

### 10.2 创建或恢复评价

1. 校验目标类型、目标存在性、评分范围和步长；
2. 对“用户 + 目标”评价记录执行 `FOR UPDATE`；
3. 没有记录则新增；
4. 已有正常记录则拒绝重复评价；
5. 已有软删除记录则原位恢复，而不是插入第二条；
6. 在同一数据库事务中原子更新目标的平均分和评分数；
7. 事务提交后删除相关缓存，并触发 AI 摘要刷新。

### 10.3 为什么评分聚合不能在 Java 中先读后算

如果两个用户同时评价，二者都可能读到相同旧值，随后互相覆盖。项目通过单条条件 SQL 更新 `avg_score/score_count`，让计算在数据库内原子完成。修改评价时替换旧分数，删除评价时扣除旧分数，并特别处理只剩一条评价的情况。

### 10.4 评价点赞

实现与动态点赞相似：关系在 `review:like:{reviewId}` ZSet，计数在 `tb_review.like_count`。Redis 操作结果决定 MySQL 是否增减，失败时执行补偿。删除评价后，在事务提交后清理点赞 Key。

## 11. 场次详情与座位图

### 11.1 三层数据模型

理解选座必须区分三层：

- `tb_seat`：影厅的物理座位模板，例如 3 排 5 座；
- `tb_showtime`：某电影或活动在某场馆、某影厅、某时间的一场演出；
- `tb_showtime_seat`：该场次下每个座位的价格与售卖状态。

物理座位坏了是 `Seat.base_status`；某一场次的座位是否可售是 `ShowtimeSeat.status`。二者不能混为一谈。

### 11.2 查询步骤

1. 校验 showtimeId；
2. 场次必须是电影或活动、在售、尚未开场；
3. 加载 Venue、Hall 和 Movie/Activity，检查关联一致；
4. 一次查询影厅全部启用物理座位；
5. 一次查询该场次对应的全部 ShowtimeSeat；
6. 以内存 Map 按 seatId 合并，避免 N+1；
7. 缺少或重复场次座位记录视为数据损坏，不能擅自当成可售；
8. 返回排、列、座位号、类型、场次价格和销售状态。

状态含义：`0=可售`，`1=未支付订单占用`，`2=已售`。Redis 五分钟临时锁不会改这里的状态。

## 12. Redis 原子锁座

### 12.1 为什么不用普通 Java 循环 SET

一次可能选择多个座位。如果逐个判断、逐个 SET，中途失败会留下半套锁。Lua 脚本在 Redis 单线程中整体执行，使“全部成功或全部失败”成为一个原子操作。

### 12.2 锁座步骤

1. 必须登录，每次最多 6 个座位；
2. 去重并排序 seatIds，使同一集合有统一表示；
3. 校验场次仍可售、座位属于该影厅且物理状态启用；
4. 校验 MySQL 中所有 ShowtimeSeat 仍为 `AVAILABLE`；
5. 先检查是否是同一用户、同一场次、完全相同座位集合的重复请求；
6. 如果是重复请求，返回原 lockToken，且不刷新 TTL；
7. 新请求生成不可预测的 lockToken 和统一的五分钟绝对过期时间；
8. Lua 先检查所有 `seat:lock:{showtimeId}:{seatId}` 都不存在；
9. 全部可锁后写入每个座位 Key，value 都是 lockToken；
10. 写入 `seat:lock:token:{lockToken}`，value 是 userId、showtimeId、seatIds、expireTime 元数据；
11. 所有 Key 使用同一个绝对过期时间。

### 12.3 主动释放步骤

1. 客户端只提交 lockToken，不提交“想删哪些座位”；
2. 从 token 元数据获得真正的座位范围；
3. 校验锁属于当前用户和当前场次；
4. Lua 只删除 value 仍等于该 lockToken 的座位 Key；
5. 再删除 token Key；
6. token 已过期时重复释放直接成功。

按 value 条件删除很重要：旧请求不能误删座位后来产生的新锁。

## 13. 创建订单：把临时锁转换为数据库事实

### 13.1 创建前校验

1. 请求携带 showtimeId、seatIds 和 lockToken；
2. 先按 lockToken 查询 `tb_ticket_order`；
3. 如果已有订单，再核对用户、场次和座位集合，匹配则直接返回原订单，实现接口幂等；
4. 如果没有订单，读取 token 元数据；
5. 校验用户、场次、座位集合、过期时间；
6. 批量读取每个 seat lock Key，要求 value 全部等于 lockToken。

### 13.2 数据库事务

1. 对场次行加锁，并重新校验场次可售；
2. 查询所选 ShowtimeSeat，要求仍为可售；
3. 从 ShowtimeSeat 读取价格快照，计算总金额；
4. 订单支付截止时间取“当前时间 + 15 分钟”和“开场时间”中更早者；
5. 插入 `tb_ticket_order`，永久保存 lockToken；
6. 批量插入 `tb_ticket_order_item`，一座位一明细；
7. 条件更新全部座位：只有 `status=0 AND lock_order_id IS NULL` 才能改成订单占用；
8. 受影响行数必须等于座位数，否则整个事务回滚；
9. 条件扣减 `available_seats`，必须恰好更新一行；
10. 提交事务。

`tb_ticket_order.lock_token` 有唯一索引。两个并发请求即使都通过前置校验，数据库也只允许一个订单消费它；另一个捕获唯一键冲突后重新查询并返回已创建订单。

### 13.3 提交后清理 Redis

数据库提交成功后，按 lockToken 所有权条件清理 Redis 锁，并最多重试两次。清理失败只记录错误，不能回滚已经提交的订单，因为 MySQL 已经是最终事实，而 Redis 锁稍后也会 TTL 过期。

## 14. 订单状态机

### 14.1 状态流转

```text
创建订单：UNPAID + 座位状态 1

UNPAID --支付--> PAID + 座位状态 2
UNPAID --主动取消/超时--> CANCELED + 座位状态 0
PAID --整单退款--> REFUNDED + 座位状态 0
```

### 14.2 支付

当前是模拟支付，没有接真实支付网关：

1. `SELECT ... FOR UPDATE` 锁订单；
2. 校验订单属于当前用户、状态为 UNPAID 且未过期；
3. 按 orderId 条件把对应座位从状态 1 改成状态 2；
4. 条件更新订单 `UNPAID -> PAID` 并记录 payTime；
5. 重复支付已支付订单时返回原结果，保证幂等。

### 14.3 主动取消与超时取消

主动取消和后台超时取消复用同一个资源释放逻辑：

1. 锁订单并确认仍为 UNPAID；
2. 查询订单明细得到座位集合；
3. 只有 `status=1 AND lock_order_id=当前订单` 的座位才能释放；
4. 恢复 `available_seats`；
5. 条件更新订单为 CANCELED；
6. 每分钟运行的定时任务每批扫描最多 100 个过期订单，逐个取消，一个失败不影响整批。

### 14.4 退款

1. 锁 PAID 订单和订单明细；
2. 必须尚未开场；
3. 任意一张票已经核销时整单不允许退款；
4. 将已售座位从 2 恢复为 0，并清除 lock_order_id；
5. 恢复余票；
6. 订单改为 REFUNDED；
7. 所有订单明细票状态改为 REFUNDED；
8. 上述操作在同一事务中完成。

## 15. 出票与场馆核销

### 15.1 为什么一张座位对应一张票

一个订单可以有多个座位，核销时可能只使用其中一张。因此 ticketCode 和 ticketStatus 放在 `tb_ticket_order_item`，而不是订单主表。

### 15.2 出票步骤

1. 锁订单，要求属于当前用户且状态为 PAID；
2. 查询全部订单明细；
3. 对尚未出票的明细生成随机唯一 ticketCode；
4. 批量条件更新 `PENDING -> VALID`；
5. 已经全部出票时直接返回原票码，实现幂等。

### 15.3 核销步骤

1. 场馆员工登录并提交 ticketCode；
2. 定位订单明细，再锁订单和票明细；
3. 通过 Showtime 找到票所属 Venue；
4. 查询 `tb_venue_staff`，要求当前用户是该 Venue 的启用员工；
5. 校验订单为 PAID，票为 VALID，且未退款、未核销；
6. 校验座位属于对应影厅；
7. 用条件更新把票 `VALID -> USED`，同时记录 usedTime 和 usedByUserId；
8. 并发重复核销只有一个请求能更新成功，其他请求根据最终状态返回“已使用”。

退款与核销都锁订单，再处理票明细，采用一致的加锁顺序，减少死锁并保证“核销成功”和“退款成功”不能同时发生。

## 16. 场馆员工管理固定座位活动场次

### 16.1 权限来源

管理权限只认 MySQL 的 `tb_venue_staff(user_id, venue_id, status=1)`，不相信客户端传来的角色，也不把 Redis 当权限事实。

### 16.2 创建场次

1. 校验员工管理该 Venue；
2. 校验 Venue、Activity、Hall 有效，Hall 属于该 Venue；
3. 对 Hall 加锁；
4. 查询该 Hall 时间段内是否已有重叠场次；
5. 读取全部启用物理座位，不能为空；
6. 插入 `tb_showtime`；
7. 按物理座位批量生成 `tb_showtime_seat`，初始状态全部可售、价格取场次基础价；
8. 两步在同一事务中完成；
9. `venueId + createRequestId` 唯一，用于并发和重试幂等。

### 16.3 停售与恢复

停售只禁止新的公开查询、锁座和下单，不取消已经存在的订单。恢复销售前会重新核对 Venue、Activity、Hall、座位总数和可售数是否一致。状态切换使用条件更新，避免两个管理员并发覆盖。

## 17. AI 评价摘要

### 17.1 能力边界

AI 功能对电影和活动的用户评价做摘要，输出：总结、优点、缺点、适合人群、注意点。它不是个性化推荐，也不参与锁座、订单和支付。

AI 默认关闭；未配置供应商时核心票务仍可运行。

### 17.2 为什么采用异步链路

模型调用慢且可能失败。如果用户发布评价时同步调用，会拉长请求并把供应商故障传给核心写接口。因此项目让评价事务只负责可靠记录“摘要需要刷新”，生成工作异步完成。

### 17.3 完整实现步骤

1. 评价新增、修改或删除在 MySQL 事务中完成；
2. 事务提交后触发 `ReviewAiSummaryTrigger`；
3. MySQL 的 `tb_ai_summary_task` 把 dirtyVersion 加一，表示有新版本待处理；
4. 向 Redis Stream `ai:review:summary:stream` 发布轻量通知；
5. 定时 Worker 用消费者组读取消息；
6. Worker 在 MySQL 中领取任务并设置租约，防止多个实例同时处理同一目标；
7. 批量读取有效评价，限制最大条数、单条字符数和总输入字符数；
8. 清洗内容，生成稳定快照、指纹和 Prompt；
9. 通过 OpenAI-compatible HTTP Client 调用模型；
10. 严格校验模型返回结构；
11. 在事务中保存不可变摘要版本，并把任务的 currentSummaryId 指向新版本；
12. 将当前摘要写入 Redis 缓存；
13. 成功后 ACK Stream 消息。

### 17.4 失败与恢复

- 可重试错误进入 `RETRY_WAIT`，按策略稍后重试；
- 不可恢复错误进入 `DEAD`；
- 评论不足时进入 `INSUFFICIENT_REVIEWS`；
- Pending 消息超时后可被其他消费者 claim；
- 对账任务会扫描 MySQL 中可恢复但可能漏通知的任务，再次投递 Stream；
- 新评价到来时旧摘要仍可返回，但标记为 `REFRESHING/stale`，直到新版本发布。

这是一套“Redis 至少一次通知 + MySQL 唯一任务事实”的最终一致性方案。Redis Stream 丢失或重复消息都不会破坏最终任务状态。

## 18. 通用异常、参数和返回值

### 18.1 统一响应

Controller 返回 `Result<T>`，成功和失败使用统一 JSON 结构；`GlobalExceptionHandler` 将 DTO 校验错误、业务异常和未知异常转换为稳定错误码。

### 18.2 为什么要区分 DTO、Entity、VO

- DTO 只描述客户端允许提交的字段；
- Entity 对应数据库字段；
- VO 只暴露前端需要看到的字段；
- 避免客户端篡改状态、价格、userId 等服务端事实；
- 避免数据库结构变化直接破坏 API。
